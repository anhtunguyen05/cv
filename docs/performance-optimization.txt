### 2. Phân tích chi phí

Toán tử spread:

```ts
[...value]

phải duyệt chuỗi theo Unicode code points và tạo một mảng mới.
Với chuỗi dài, chi phí bao gồm:
- Duyệt toàn bộ chuỗi.
- Tạo nhiều phần tử mảng.
- Cắt mảng.
- Ghép lại thành chuỗi.
- Giải phóng object trung gian qua garbage collection.
Trong khi đó, phần lớn thao tác nhập liệu thông thường chỉ thêm một vài ký tự vào cuối chuỗi.
3. Hướng tối ưu thứ nhất: Fast path
Nếu UTF-16 string length nhỏ hơn hoặc bằng giới hạn code points, chắc chắn số code points cũng không vượt giới hạn.
Vì vậy:
function limitCodePoints(
  value: string,
  limit: number,
): string {
  if (value.length <= limit) {
    return value
  }

  let count = 0
  let endIndex = 0

  for (const codePoint of value) {
    if (count >= limit) break

    endIndex += codePoint.length
    count++
  }

  return value.slice(0, endIndex)
}

Ưu điểm:
- Với phần lớn input chưa đạt giới hạn, không cần tạo mảng.
- Khi cần cắt chuỗi, vẫn đếm đúng Unicode code points.
- Giảm allocations so với spread/slice/join.
4. Hướng tối ưu thứ hai: Giảm số lần encoding
Có một điểm đáng chú ý về hai giới hạn hiện tại.
Một Unicode code point hợp lệ khi encode UTF-8 chiếm tối đa 4 byte.
Với giới hạn 50.000 code points:
50.000 × 4 byte = 200.000 byte

Trong khi giới hạn thứ hai là:
200 KiB = 204.800 byte

Do đó, nếu chuỗi đã được giới hạn ở tối đa 50.000 Unicode code points, kích thước UTF-8 của chính chuỗi đó không thể vượt 204.800 byte.
Tức là trong cấu hình giới hạn hiện tại, phép kiểm tra 200 KiB thực chất bị giới hạn 50.000 code points bao phủ.
Đây là một cơ hội tối ưu rõ hơn việc đơn thuần debounce TextEncoder.
Có thể bỏ kiểm tra byte khỏi hot path của UI sau khi xác nhận backend cũng đang áp dụng đúng cách đếm và không có phép biến đổi dữ liệu làm tăng kích thước trước khi validate.
Vẫn có thể giữ server-side byte validation như cơ chế phòng vệ, đặc biệt nếu giới hạn thay đổi trong tương lai.
5. Hướng tối ưu thứ ba: Không debounce toàn bộ form state
Không nên debounce rawText vì:
- Người dùng cần thấy dữ liệu vừa nhập ngay lập tức.
- Dirty checking cần phản hồi chính xác.
- Save không được lấy giá trị cũ do debounce chưa hoàn tất.
Nếu sau tối ưu vẫn có validation phức tạp, hãy debounce validation computation, không phải source-of-truth của input.
6. Acceptance criteria
- Nhập JD dài không tạo mảng Unicode code points ở mọi lần cập nhật.
- Không cắt sai emoji hoặc surrogate pairs.
- Không làm thay đổi giới hạn 50.000 code points.
- Save luôn lấy nội dung mới nhất.
- Không có input lag đáng kể ở dữ liệu gần giới hạn.

2. Vấn đề
mousemove có thể được phát với tần suất cao.
Mỗi event có thể dẫn đến:
mousemove
    ↓
Update reactive state
    ↓
Invalidate render dependency
    ↓
Vue patch style
    ↓
Browser paint

Không phải mọi event đều dẫn đến một lần DOM patch độc lập vì Vue có batching. Dù vậy, đưa vị trí chuột vào component reactivity vẫn tạo công việc không cần thiết cho một hiệu ứng trang trí.
3. Hướng sửa
Dùng CSS variables kết hợp requestAnimationFrame.
let frame = 0
let x = 0
let y = 0

function onMouseMove(event: MouseEvent) {
  x = event.clientX
  y = event.clientY

  if (frame) return

  frame = requestAnimationFrame(() => {
    frame = 0

    const element = cardRef.value
    if (!element) return

    const rect = element.getBoundingClientRect()

    element.style.setProperty(
      '--spotlight-x',
      `${x - rect.left}px`,
    )

    element.style.setProperty(
      '--spotlight-y',
      `${y - rect.top}px`,
    )
  })
}

CSS:
.template-spotlight {
  background: radial-gradient(
    250px circle at
      var(--spotlight-x, 50%)
      var(--spotlight-y, 50%),
    color-mix(
      in srgb,
      var(--color-primary) 9%,
      transparent
    ),
    transparent 70%
  );
}

Dùng CSS hover hoặc class để điều khiển opacity.
Cần bổ sung cleanup của animation frame khi unmount và hỗ trợ prefers-reduced-motion nếu animation gây khó chịu.
4. Trade-off
Cập nhật CSS variables vẫn có thể gây style recalculation/paint. Không nên kỳ vọng chi phí rendering bằng không.
Với số lượng template ít, đây là micro-optimization. Chỉ nên ưu tiên sớm nếu Chrome Performance cho thấy hiệu ứng gây dropped frames hoặc main-thread work đáng kể.

Kết luận kỹ thuật
Hướng đi tốt nhất cho CareerFitCV hiện tại là tối ưu theo nguyên tắc: Fetch less, compute less, render only what matters, and cache deliberately.
Trong đó:
- Fetch less: API chỉ trả dữ liệu cần thiết cho từng màn hình.
- Compute less: Không clone hoặc validate toàn bộ document cho một thay đổi nhỏ.
- Render only what matters: Chỉ tối ưu component updates sau khi xác định hot path.
- Cache deliberately: Cache theo tính chất dữ liệu, không dùng một chính sách cho tất cả.
Nếu triển khai đúng thứ tự, dự án có thể cải thiện cả network, CPU, memory và khả năng mở rộng mà không cần thêm framework hoặc thay đổi kiến trúc frontend nền tảng.
